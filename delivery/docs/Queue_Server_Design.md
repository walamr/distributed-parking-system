# Queue Server Design

This document details the design and architecture of the Event Queuing System for the Mulligan Parking System, primarily fulfilling Task 2 of the project.

## Overview
As a distributed parking system, Mulligan uses RabbitMQ as a centralized Message Broker to capture and route critical events asynchronously from user interfaces to interested downstream consumers.

The system declares a main Direct Exchange and binds two primary Event Queues to it:
1. `transactions_queue`: Holds records of paid parking events.
2. `citations_queue`: Holds parking citations generated by Parking Enforcement Officers (PEOs).

## System Architecture
* **Queue Configuration via Spring AMQP**: The `queue-service` behaves as a configuration sentinel on startup. It uses Spring Boot's AMQP integration (`RabbitMQConfig.java`) to idempotently connect to the `mulligan-rabbitmq` Docker container and establish the necessary topology (Exchanges, Queues, Bindings).
* **AMQP Producers (UIs)**: The `Customer UI` and `PEO UI` encapsulate a pure `amqp-client`-based wrapper (`RabbitMQClient.java` in the `common` module). As per the strict architectural constraints, these UIs communicate with the REST API to persist state, and then *natively* establish an AMQP connection to route the resulting event payloads directly into the RabbitMQ Exchange. The Database service is explicitly decoupled from RabbitMQ.
* **AMQP Consumer (MO UI)**: The `MO UI` is responsible for generating municipality transaction & citation reports. Upon a report request, it connects to the RabbitMQ broker via the same `RabbitMQClient`, drains the relevant queues (`transactions_queue` or `citations_queue`), and appends the messages to an aggregated in-memory MO Report view.

## Queue Topology
1. **Exchange Name**: `mulligan-exchange` (Type: Direct, Durable: False)
2. **Queues & Bindings**:
    - **Name**: `transactions` (Durable: True)
      **Routing Key**: `transactions`
    - **Name**: `citations` (Durable: True)
      **Routing Key**: `citations`

## Payloads
Messages are serialized into strict JSON representations of the `TransactionReportMessage` and `CitationReportMessage` objects using Jackson.

### Transaction JSON Example (transactions queue)
```json
{
  "vehicleNumber": "412-60-971",
  "parkingSpaceId": "10",
  "parkingZone": "Adams Ave",
  "date": [2026, 4, 19],
  "startTime": [13, 1],
  "stopTime": [13, 15],
  "amountOwed": 55.27,
  "generatedAt": [2026, 4, 19, 13, 15, 0]
}
```

### Citation JSON Example (citations queue)
```json
{
  "vehicleNumber": "412-60-971",
  "parkingSpaceId": "11",
  "parkingZone": "Magnolia Way",
  "date": [2026, 4, 19],
  "inspectionTime": [13, 18],
  "amountOwed": 100.00,
  "generatedAt": [2026, 4, 19, 13, 18, 0]
}
```

## Security & Resilience considerations
The Queue services operate fully internally on the `mulligan-network` bridge interface over AMQP port `5672` in standard unencrypted format to streamline local execution. Real-world adaptations are expected to encrypt this AMQP layer over TLS (port 5671) per standard architectural progression.
